# Результаты оценки модулей (план, E-2)

> Шаблон. Заполняется **по результатам** прогонов (`evaluation/runner`, см. `evaluation/README.md`).
> До первого реального прогона на развёрнутом стенде (`infra/scripts/up.sh`) в этом файле нет ни одного
> числа — только структура, которую предстоит заполнить, и то, что уже решено заранее (пороги, состав
> эндпоинтов, список известных ограничений). Числа **не подбираются заранее под желаемый результат**:
> каждая таблица — прямой вывод `report.md`/`report.csv` соответствующего прогона.

## Как читать эту таблицу

Все числа — из `manifest.json` конкретного прогона (коммит, sha256 ground-truth, хост, повторы,
порог). Ссылка на директорию прогона (`evaluation/runs/<timestamp>/`) указывается при каждой таблице
модуля, чтобы результат был воспроизводим и проверяем (план, E-1.5/E-1.6).

Порог по умолчанию — `LIKELY` (findings с `verdict < LIKELY`, т.е. `SUSPECTED`, не считаются
позитивными). Чувствительность к порогу считается дополнительно для `SUSPECTED` и `CONFIRMED`
(план, E-1) — см. раздел «Чувствительность к порогу» под каждым модулем.

### Известные ограничения E-3

- Ни один из сценариев E-3 не запускался вживую в этой сессии (нет Docker/живого стенда и
  установленного браузера Playwright в среде разработки) — тесты написаны и статически
  проверены по исходному коду frontend/Core, но не исполнялись; см.
  `vulscan-frontend/tests/e2e/README.md`.
- E2E-02 жёстко предполагает `maxActiveScansPerUser=2` (значение по умолчанию в Core); если
  `.env` стенда его переопределяет, нужно передать `E2E_MAX_ACTIVE_SCANS_PER_USER`.
- E2E-05 может упасть из-за гонки (скан успевает завершиться раньше нажатия "Отменить") —
  осознанное решение не маскировать это retry, см. комментарий в `cancel-scan.spec.ts`.

## Известные ограничения экспериментов (переносятся из кода/README по мере обнаружения)

- `RunManifest` фиксирует коммит только `vulscan-infra` (сам runner), не остальных пяти репозиториев —
  SHA каждого фиксируется здесь вручную при заполнении таблиц выше.
- Time-based SQLi — отдельная строка из-за другой нагрузки (искусственные задержки), не для
  прямого сравнения с error/boolean-based по времени/запросам.
- IDOR-FP02 (протухающая сессия) — наиболее хрупкий случай матрицы доступа; при нестабильности
  между повторами проверить порядок обработки ресурсов в `evaluation/scenarios/idor.yaml`.
- Негативная цель "clean" — второй инстанс lab-app, поднимается отдельно от обычной среды N-1
  (`infra/docker-compose.lab-clean.yml`), не входит в `infra/scripts/up.sh`.
